## 0. 不变量（M1 不许破坏的东西）

1. **契约零变化**：`/v1/systemone` 的字段名、响应形状、错误码语义与 M0 一致（仅按 §5 收窄两处语义）。
2. **问题相互独立**（官方明文）：**不得**让问题 A 的答案进入问题 B 的 prompt。前缀复用只共享 `state` 前缀，不共享答案。
3. **只承诺「答案被约束在调用方给的选项集合内」**，不写「不能幻觉 / 不会出错」。
4. 概率仍只覆盖声明槽位、仍按 6 位小数取整、`Σp = 1 ± 1e-6`。
5. 纯 Rust；产品运行时不引 Python（基准与验收脚本可用 shell/python，但**基准主体是 Rust bin**）。

## 1. 端点事实（2026-09-19 实测 `115:8014`，本规格的依据）

| 事实 | 实测值 |
|---|---|
| 单条补全（241 prompt tokens / `max_tokens=1` / `logprobs=10`） | **0.56 s**，`usage.prompt_tokens=241` |
| **`prompt` 传数组（批量）** | **支持**：一次请求 3 个 prompt（722 tokens）→ 200，返回 **3 个 choices**，每个带自己的 `top_logprobs`，耗时 **0.45 s** |
| ⇒ 共享前缀的收益 | 3 份共享前缀的请求总耗时 < 1 份的耗时 ⇒ 服务端（SGLang radix cache）把 `state` 前缀**只 prefill 一次**。这是 ≥3× 的机制来源 |
| 计费口径 | `usage.prompt_tokens` 按 N × 前缀累加（**不因缓存而减少**）⇒ **收益看墙钟，不看 token 数**；报告里必须写清这一点，不许拿 token 数冒充加速 |
| `top_logprobs` 形状 | `list`，`[0]` 是 `{token 文本: logprob}` 映射（与 M0 一致） |
| ⚠️ 同 state 的题目 top-k **可能不含某个声明槽位** | 实测：某 choice 题（A: no / B: yes）的 top-10 = `B, The, **, Based, yes, Answer, Yes, -…`——**没有 `A`** ⇒ 见 §5② |

## 2. M1-1 批处理读出头（backend）

`crates/jev-backend/src/lib.rs` 的 `DecisionBackend` **新增**（带**默认实现**，不破坏已有实现类）：

```rust
/// Read the answer-slot distribution for N prompts in one shot.
/// Default: sequential `token_logprobs` per prompt (correct, slow).
async fn token_logprobs_batch(&self, prompts: &[String], top_k: usize)
    -> Result<Vec<Readout>, BackendError> { /* 顺序循环 */ }
```

- `OpenAiCompatBackend` **覆写**：一次 POST，`prompt` 为**数组**；解析要求：
  - `choices.len() == prompts.len()`，否则 `BackendError::Decode`（**不许部分成功**）；
  - 按 `index` 字段排序后再对齐到输入顺序；
  - 任一元素缺 `logprobs`/`top_logprobs` 为空 → 整个调用 `NoLogprobs`；
  - HTTP 非 2xx → `Http`（沿用 M0 的 char 安全截断）。
- `MockBackend` 也要能按批量语义工作（测试用）。
- **top_k**：`max(n_slots_max + 5, 100)`。下限是**实测值**不是猜的：`20` 时真端点每 126 次读数有 8 次
  缺声明槽位（约 6% 的请求会 422），`100` 时同负载 126/126、210/210 全覆盖，
  而每判断中位延迟只变 +1%（226→228 ms）。详见 §4.1 末段。

## 3. M1-2 服务端调度（前缀复用的落点）

`/v1/systemone` 的处理顺序改为：

1. 渲染全部问题（每题一个完整 prompt = `state` 前缀 + 题目后缀 + `Answer:`）。
2. 逐题做槽位校验（`verify_slots`），保持 M0 的 422 路径。
3. **一次**批量读出头（`token_logprobs_batch`）——所有问题天然共享同一个 `state` 前缀。
4. 组装答案（概率数学、legend、usage 全部沿用 M0 的 core 函数）。

- 单问题请求也必须走同一条码路（**不得**退化成两次调用）。
- 题目顺序无关：答案按 `questions` 的 key 回填；重复请求结果必须逐位一致（M0 已有断言，保留）。
- 批量调用失败时**不做**逐题降级重试（那会掩盖问题）；直接按 §5② 的错误码返回。

## 4. M1-3 基准（硬指标门）

**产物**：`crates/jev-server/src/bin/jev-bench.rs`（纯 Rust，无 Python 运行时依赖）

```
jev-bench --base-url http://10.10.10.115:8014/v1 --model qwen3.8-27b \
          --state-file bench/states/long-state.txt --questions 21 [--repeat 3]
```

- 生成 21 个问题（`choice`/`score`/`noul` 混合，同一 `state`）。
- **基线（fresh）**：逐问题独立请求 → 每题一次完整 prefill + 解码。
- **优化（shared-prefix）**：单请求批量（`prompt` 数组）→ 共享一次 prefill。
- **协议：两条臂按轮交错**（fresh 一轮全部题目 → 立刻 shared 一轮 → 下一轮），
  并报每轮 fresh/shared 比值。理由见 §4.1：本端点与他人共享，分块计时会**把抢占尖峰记成路径属性**。
- 每路重复 `--repeat` 次，报 **p50 / p95 / 判断每秒 / 加速比**；两组原始耗时数组一并落盘
  `bench/results/<utc-date>-<host>.json`（含端点、模型、参数、SGLang 版本若有）。
- **验收门：加速比 ≥ 3×（21 问题）** ← **该门已于 2026-09-19 判定在当前端点上不可达，见 §4.1；
  未达标不得含糊，必须按 §4.1 重述的方式报**。达不到就如实报，不许调参凑数（不许拿掉预热、不许改问题数）。
- 报告必须同时给：**墙钟口径 + token 口径**（§1 的计费说明），并说明加速里有多少来自批处理、多少来自前缀缓存。
- 4090（115:8014）出一张表；**M3 Ultra 表待本机后端就绪后再出，本轮明确记为未完成**。

### 4.1 2026-09-19 修订：≥3× 门未达标，及其原因（**实测记录，不许删改**）

**实测（21 题，真端点 `115:8014`，SGLang 0.5.19，`top_k=100`，交错协议，5 轮）：**

| 口径 | fresh（逐题独立请求） | shared（单请求批量） | 比值 |
|---|---|---|---|
| 总墙钟（105 判断） | 34.06 s（3.08 判断/秒） | 35.62 s（2.95 判断/秒） | **0.96×** |
| 交错后每轮比值 | — | — | 0.95 / 0.95 / 0.99 / 0.92 / 0.98 |
| 每判断延迟（p50） | 300 ms | — | — |

**分块计时（改协议前）同族负载连续四次跑出 1.50× / 2.23× / 0.88× / 1.06×** ——
噪声横跨 0.88～2.23，说明单看一个数字毫无意义；交错后才收敛到 0.92～0.99。

**结论：在本端点上，显式批量的加速比 ≤ 1（约低 4%）。原因（三条，均已取证）：**

1. **基线已被服务端的 radix 前缀缓存救过。** 本门原文假定基线是"逐问题**重编码**"。但 SGLang
   自带内容寻址前缀缓存：fresh 路径的 63 个请求共享同一 `state` 前缀，服务端**只 prefill 一次**，
   之后全部命中缓存 —— 我假定的那个"重编码基线"在这个端点上**根本不存在**。批量本可省下的
   prefill，早被基线白拿了。
2. **批量只换来一条串行尾巴。** 单请求里排 21 条，延迟取**最慢那条**（max 而非 mean）；
   服务端一次卡顿同时拖住 21 条。实测 token 口径完全相同（两臂均 31555 prompt tokens /
   105 completion tokens）——**decoder 步数一次都没少**。
3. **真正的成本不在 prefill。** 232 token 的 prompt 生成 1 个 token 约 300 ms，瓶颈在
   **152k 词表的 top-k logprob 计算 + 每请求开销**；前缀复用碰不到这块。

**⇒ 门的重述（自本日起生效）：**

- **在"服务端自带前缀缓存、且客户端无法关闭"的端点上，不得声称前缀复用带来加速**；
  此时前缀复用是**服务端的既有能力**，不是本项目的成果。此处只允许报实测的 ≤1 比值与上述原因。
- **前缀复用要成为本项目的可测硬指标，必须满足其一**：
  (a) 基线可关闭缓存（自持后端 / `--disable-radix-cache` 的独占实例）；或
  (b) 用**prefill 工作量口径**（cached vs uncached tokens）而非墙钟；或
  (c) 在**我们自己的后端**（设计里 M1 的 llama.cpp FFI 路径）上测 —— 那里 KV cache 归我们管，
  基线可以真的"逐问题重编码"。这正是设计把 FFI 放进 M1 的原因，也说明这条门**本就不该写在
  8000 端口的 OpenAI 兼容端点上**。
- 因此本项**不标记为"已达成"**：标记为"**在共享端点上限成立、待自有后端复测**"。
  在 (a)/(b)/(c) 任一落地前，不得在任何对外材料里写"前缀复用提速 N 倍"。

**另一项本轮修掉的真缺陷（与加速比无关，属产品正确性）：**

`top_k` 原规则 `max(n_slots+5, 20)` 在真端点上**每 126 次读数就有 8 次缺声明槽位**
（118/126）⇒ 真服务路径会有约 6% 的请求以 `SlotMissingFromTopK` 422 失败。
实测把下限提到 **100**：同负载覆盖率 **126/126（另一次 210/210）**，而每判断中位延迟只从
226 ms 变到 228 ms（+1%）。**故 §2 的 top_k 规则改为 `max(n_slots+5, 100)`**
（`api.rs` 与 `bench.rs::top_k_for` 同步，测试同步）。
- 报告必须同时给：**墙钟口径 + token 口径**（§1 的计费说明），并说明加速里有多少来自批处理、多少来自前缀缓存。

## 5. M0 遗留项（M1 就地收口）

### ① `>26` 选项：专属错误变体
`crates/jev-core/src/error.rs` 新增变体（M0 的冻结只对 M0 生效，M1 放开）：

```rust
/// More options than M0's single-letter slots can name (max 26).
TooManyLetterSlots { id: String, got: usize, max: usize },
```

- 语义/Display 与 422 对齐；`choice` 的 `>255` 仍走 `TooManyChoiceOptions`（保持 M0 行为）。
- 必须删除 `render.rs` 里**复用 `PromptTooLong`** 的写法（那是语义错位：prompt 一个字都没超长）。
- 测试：27 选项 → `TooManyLetterSlots`；255 选项 → `TooManyChoiceOptions`；256 选项 → `TooManyChoiceOptions`。

### ② 缺槽位 与 422/502 的分工（**决策**）
- top_k 提升到 `max(n+5, 20)`，降低"声明槽位不在 top-k 里"的概率（§1 实测确实发生过）。
- 仍缺 → **422 `SlotMissingFromTopK`**。理由：缺槽位意味着该选项的**概率未知**；把它当 0 或把概率在剩余槽位上重新归一化都会**编造数字**，违背校准优先的定位。
- **422 与 502 的分工**（写进 README 的契约说明）：
  - **422** = 输入或读数不成立（空 questions、选项数越界、档位越界、prompt 超预算、槽位缺失）；
  - **502** = 后端调用失败（HTTP 错误、响应无法解析、连接失败）。
- 测试：缺槽位 → 422；后端 500 → 502；后端返回非法 JSON → 502。

### ③ `JEV_TOKENIZER` 本地 `tokenizer.json` 回退
- 目标：端点没有 `/tokenize`（或端点不可达）时，用本地 `tokenizer.json`（`tokenizers` crate）做同样的三断言校验。
- **前置检查**：`tokenizers` 及其依赖是否在本机离线 cargo 缓存里。**不在 → 不得联网拉**（本机 cargo TLS 是坏的），此时在报告里明确记为"被离线缓存阻塞"，并把 `JEV_TOKENIZER` 的文档注释写成「未实现 + 原因」。
- 若实现：`JEV_TOKENIZER=/path/tokenizer.json` → 启动自检走本地路径；两条路径的**断言完全相同**（单 token + 边界不变 + 探针 id 可配）。

### ④ score 的 `labels` 语义（冻结缺陷）
`RenderedQuestion::labels` 对 `score` 现在存**序号字符串**（`"0"`），逼得 `api.rs` 回头读原始 `criteria` 才能给 `legend`。
M1 改为：`labels` 对 `score` 存**渲染后的档位描述文本**；`slots` 不变（仍是序号字符串，那是给调用方的值）。
同步更新 M0 的相关断言测试，并在提交信息里写明这是**有意的语义变更**。

## 6. M1-4 校准评测骨架（M2 的主体不在此范围）

- `crates/jev-eval`：题集冻结（**内容 hash 写进 manifest**）+ 指标（平衡准确率 / NLL / Brier / **ECE + 可靠性曲线**）+ `verify` 子命令：
  **从落盘的结果文件重算报告里的每一个数字**（照 SemIf 的 `verify_published.py` 做法）。
- 题目来源分层上报，**禁止合并成一个总分**；中文集与英文集分开报。
- 本轮落一个**起步题集**（中文，含四类：证据判断 / 规则应用 / 候选选择 / 缺失证据）；
  规模若未达设计里的 ≥150 行，**必须在报告与 README 里写明实际条数与差距**，不许含糊。
- 验收：一条命令重跑，数字与提交结果一致（逐位）。
